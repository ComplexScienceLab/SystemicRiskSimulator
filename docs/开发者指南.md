# SRS 开发者指南

## 一、目标与适用范围

SystemicRiskSimulator，简称 SRS，是一个以“配置驱动实验编排”为核心思想的系统性风险模拟器。它的设计重点不是把所有研究逻辑都塞进一个主程序，而是把不同职责拆成两层：

1. Simulator 内核负责统一入口、配置合成、路径解析、阶段调度、实验快照、结果导出与运行模式切换。
2. 四件套 library 负责具体实验内容，即配置、初始个体、参数组合、模型机制本体。

这份开发者指南面向两类开发者：

1. 开发 Simulator 内核的人：修改 main.py、programs、core、tools，使调度能力、导出能力、通用算法与基础设施变得更稳定。
2. 开发具体实验库的人：围绕某个模型家族或某个实验工程，开发 configs_library、agents_library、parameters_library、models_library 这四件套资源，使 SRS 能在不改核心调度器的前提下运行你的实验。

本指南的目标不是提供零散建议，而是给出一套当前代码已经在使用的正式开发契约。只要你要为 SRS 新增模型、迁移外部工程、维护 Samples、或把 SystemicRiskLab 之类外部工程挂接到 SRS，本文件都应该作为第一阅读材料。

本指南覆盖以下主题：

1. Simulator 的真实执行链路和权威入口。
2. 四件套 library 的职责边界、目录规范、命名规范和接口规范。
3. 开发者必须遵守的生成方式、导入方式、快照方式与禁止事项。
4. 如何新增一个模型家族，如何调试，如何验证，如何避免把临时脚本和临时数据演变成正式入口。

## 二、先理解 SRS 的基本设计思想

SRS 的核心不是“某个单独模型”，而是“用统一的调度器运行不同的模型库”。

你可以把它理解为一个五层结构：

1. CLI 层：负责接收命令行参数，选择实验，接收覆盖项。
2. 配置合成层：把 global config、experiment JSON、set_config_variables.py 和 override 组合成最终 config。
3. 运行组织层：根据运行方式决定是否执行实验主程序、预处理程序、可视化程序，以及是否在当前进程运行。
4. 实验资源层：四件套 library，分别提供 config、agents、parameters、models。
5. 模型执行层：具体模型代码、状态更新、财务变量更新、策略决策、结果收集。

这套结构有两个必须长期坚持的原则。

第一，开发 Simulator 时要尽可能把“通用编排能力”留在内核，把“实验具体内容”留在四件套库里。不要每来一个模型就往 main.py 塞分支，也不要把某个具体实验的路径和文件名写死在 core 目录中。

第二，开发具体实验时要尽可能遵守 SRS 已有接口，而不是绕开四件套自己发明一条“临时快跑路径”。临时脚本可以存在于开发阶段，但不能替代正式入口、正式配置、正式四件套产物，更不能让主流程依赖临时脚本才能运行。

## 三、真实执行链路

### 3.1 权威入口

当前权威入口是 SystemicRiskSimulator/main.py 中的两个对象：

1. main(argv=None)：CLI 入口。
2. simulator(config)：一次实验调度的总入口。

推荐运行方式是：

```powershell
python -m SystemicRiskSimulator.main --global-config config.json --experiment ib2111
```

不要把 experiments_program.py、transform_output_data_program.py、visualize_data_program.py 当成新的用户级入口长期直接暴露。它们是阶段程序，不是项目的总入口。开发和调试时可以单独调用，但正式使用和正式文档都应从 main.py 出发。

### 3.2 配置来源的优先级

main.py 负责把不同来源的配置整理成一个最终 config。当前支持三种选择实验的方式：

1. global config + experiment 键名。
2. experiment JSON。
3. set-config-folder，直接指定 set_config_variables.py 所在目录。

之后再叠加 override。最终只有一个 dict 被交给 simulator(config)。

注意一个很关键的事实：真正决定实验运行细节的权威对象仍然是 set_config_variables.py 里导出的 set_config_variables 字典。simulator(config) 会先导入 set_config_variables，再把前面合成的 config 叠加进去。因此：

1. folderpath_config 是硬性必需字段，没有它就无法导入实验配置。
2. experiment JSON 不是纯配置替代层，它更像“选择配置目录并补少量覆盖字段”的辅助入口。
3. 只有字段名与最终 config 契约一致时，experiment JSON 中的键才会真正生效。

这也是为什么当前 Samples/exp 里的某些字段，例如 folderpath_model、output_subdir，更适合被理解为样例辅助信息，而不是 SRS 的强契约。当前主流程真正读取的是 folderpath_models，而不是 folderpath_model。开发者写新实验 JSON 时，必须按真实代码使用的字段名写，不能以为样例 JSON 出现过的字段都会生效。

### 3.3 运行时阶段

导入 set_config_variables.py 之后，simulator(config) 会做这些事：

1. 计算 project root、simulator root、output root。
2. 根据 folderpath_models、folderpath_config、folderpath_parameters、folderpath_agents 计算四件套真实目录。
3. 根据 is_use_Gym_environments、is_use_RL_method、RL_state 决定“运行实验组的方式”。
4. 为实验输出目录创建 outputlog、config、agents、parameters、models 等快照目录。
5. 快照 config、agents、parameters、models。
6. 按 schedule_operation 决定是否运行实验主程序、结果预处理、可视化。
7. 根据 is_develope_mode 选择当前进程直接 import 模块运行，或者序列化 sgv 后交给子进程执行阶段脚本。

因此，开发者在任何时候都要把“实验快照”视为 SRS 的正式产物，而不是副产品。SRS 的复现依赖于实验输出目录里保留下来的 config/agents/parameters/models 快照，这也是为什么四件套不能被临时脚本取代。

## 四、四件套 library 的职责边界

SRS 当前默认的实验资源组织方式是四件套 library：

1. configs_library：定义实验配置和阶段调度开关。
2. agents_library：定义初始个体、网络和备注数据，并生成 agents/*.pkl。
3. parameters_library：定义参数组合，并生成 parameters.pkl。
4. models_library：定义模型代码本体，包括主过程、财务更新、状态结构、可选策略模块。

它们的默认布局如下：

```text
libraries/
|- configs_library/
|  \- config_xxx/
|     \- set_config_variables.py
|- agents_library/
|  \- agents_xxx/
|     |- set_agents_variables.py
|     |- logfile.log
|     \- agents/
|- parameters_library/
|  \- parameters_xxx/
|     |- set_parameters_variables.py
|     |- parameters.pkl
|     \- parameters.xlsx
\- models_library/
   \- model_xxx/
      |- __init__.py
      |- model_main.py
      |- model_finance.py
      |- model_define.py
      \- model_strategy.py
```

这四类目录共同构成一个实验单元。它们之间的关系如下：

1. config 负责把另外三件套串起来。
2. parameters 负责生成“要跑哪些实验任务”。
3. agents 负责提供“每个任务的初始个体状态和网络初值”。
4. model 负责定义“每个任务如何从初值推进到终态”。

对开发者而言，这四件套不只是“建议的目录分工”，而是正式开发界面。也就是说：

1. 需要配置实验运行口径时，严格写在 config 的正式配置文件内。
2. 需要定义初始主体、网络和初值时，严格写在 agents 的正式生成脚本内。
3. 需要定义实验参数空间时，严格写在 parameters 的正式生成脚本内。
4. 需要定义状态演化、传播机制和策略机制时，严格写在 model 的正式类与方法内。

不要把四件套之外的临时 py、notebook、草稿脚本、一次性调试脚本当成“另一套平行开发面”。在 SRS 里，四件套就是开发者应该作答的正式答题区，其他位置只能作为短期排查工具，不能承载正式配置、正式机制和正式输入产物。

不要让其中任何一类职责漂移。

典型错误包括：

1. 把参数枚举写进 set_config_variables.py，而不是 parameters_library。
2. 把初始银行网络硬编码进 model_main.py，而不是 agents_library。
3. 为了省事写一个 tmp_run_model.py，直接拼接参数、读几个 pkl、跑几步，然后把这个临时脚本当成正式运行入口。
4. 在 README 或手册里宣传“运行某个临时脚本即可”，而不是通过 main.py 和四件套运行。
5. 在四件套目录外单独再造一套 config_temp、agents_tmp、parameters_draft、model_debug 之类平行体系。

只要你发现一段代码既在生成参数，又在生成 agents，又在临时决定模型路径，它大概率已经越界了。

## 五、目录与命名规范

### 5.1 总体命名规范

建议统一使用下列前缀：

1. config_模型名或实验名。
2. agents_模型名或实验名。
3. parameters_模型名或实验名。
4. model_模型名或实验名。

例如 Samples 中已有的：

1. config_sample_IB1111。
2. agents_sample_IB2111。
3. parameters_sample_IB1211。
4. model_sample_IB2111。

外部工程也应尽量沿用这一命名风格，因为 SRS 当前很多人类可读日志和目录判断都围绕这些命名展开。

### 5.2 配置目录命名

配置目录必须是一个目录，而不是一个散落的单文件。目录中至少要有：

1. set_config_variables.py。

不要把配置散成十几个临时 py 文件，再用 import 链串起来，除非你非常确定团队能够长期维护。对 SRS 当前结构而言，一个模型实验的“主配置”必须清晰地落在 set_config_variables.py 中。

### 5.3 agents 文件命名

当前 Operator 加载 agents 的方式不是扫描目录猜文件，而是按照 set_config_variables.py 中的两个列表字段拼文件名：

1. list_agents_data_filename_para_01：例如 BB、IB、AB、note。
2. list_agents_data_filename_para_02：例如 year、density_IB。

然后按如下格式拼接：

```text
id={id_agents}-v={变量名}-year={year}-density_IB={density_IB:.2f}.pkl
```

例如：

```text
id=0-v=BB-year=2012-density_IB=1.00.pkl
id=0-v=IB-year=2012-density_IB=1.00.pkl
id=0-v=AB-year=2012-density_IB=1.00.pkl
id=0-v=note-year=2012-density_IB=1.00.pkl
```

这意味着：

1. 生成 agents 时，文件名必须与参数表里的列完全对应。
2. 参数表中参与拼名的列，数值精度必须与文件名保持一致。
3. 不允许私自改名为 bank_001.pkl、network.pkl、meta.pkl 这类与当前加载规则不兼容的名字，除非你同步修改 Operator 的加载逻辑以及相关手册。

### 5.4 parameters 文件命名

参数库当前正式产物是 parameters.pkl，兼容回退产物是 parameters.xlsx。Operator 会优先读取 parameters.pkl，失败时回退到 parameters.xlsx。

因此正式要求是：

1. set_parameters_variables.py 必须能生成 parameters.pkl。
2. 推荐同时生成 parameters.xlsx，便于人工预览和排错。
3. 不允许只生成某个临时 csv 再让主流程手工改读那个 csv，除非你修改了 Operator 的统一读取协议。

### 5.5 model 文件命名

models_library 目录下当前约定是通过正则 [Mm]odel 导入模块内容。因此模型目录中的核心文件应保持以 model_ 开头：

1. model_main.py。
2. model_finance.py。
3. model_define.py。
4. model_strategy.py。

如果你写成 finance.py、main_logic.py、states.py，SRS 不是绝对不能跑，但你会立刻偏离现有导入习惯、团队阅读习惯和文档习惯。除非你同步升级导入器与全套文档，否则不要随意另起命名体系。

## 六、configs_library 开发规范

### 6.1 config 的职责

set_config_variables.py 的职责是描述一次实验的调度方式、目录指向、运行模式、后处理选项和可视化选项。它不应该承担以下职责：

1. 批量生成参数组合。
2. 批量写出 agents 数据。
3. 实现模型核心公式。
4. 直接作为实验主程序替代 main.py。

### 6.2 set_config_variables.py 的最低要求

一个可运行的配置至少应清楚定义：

1. folderpath_config。
2. folderpath_models。
3. folderpath_parameters。
4. folderpath_agents。
5. schedule_operation。
6. list_agents_data_filename_para_01。
7. list_agents_data_filename_para_02。
8. list_idsExperiment_to_run。
9. is_develope_mode。
10. is_use_Gym_environments、is_use_RL_method、RL_state 中与运行方式相关的字段。

除此之外，建议清晰声明：

1. folderpath_root_experiments。
2. foldername_experiments_output_data。
3. runtime_model_import_source。
4. runtime_copy_resources_into_simulator_data。
5. is_auto_confirmation。
6. test_logging。
7. test_max_num_of_turn。

### 6.3 config 中哪些字段是真正的开发契约

开发时最容易混淆的一点是，config 里既有“主契约字段”，也有“实验口径字段”。

主契约字段是指 Simulator 一定会读取并据此调度的字段，例如：

1. folderpath_models。
2. folderpath_config。
3. folderpath_parameters。
4. folderpath_agents。
5. schedule_operation。
6. is_develope_mode。

实验口径字段则更多服务于具体模型逻辑或结果后处理，例如：

1. list_idsExperiment_to_run。
2. test_turn_for_debug。
3. vis、transform_data、visulization_process。

写配置时必须优先保证主契约字段正确，再去调实验细节。

### 6.4 config 开发中的禁止事项

1. 不要在共享配置中写死本机绝对路径，尤其不要把 C:/Users/... 直接当成公共模板内容。
2. 不要在 config 里直接调用程序入口，例如 import 某个模块后立刻执行模拟。
3. 不要把多个实验共用的通用逻辑抄到十几个 set_config_variables.py 中；能提到 Simulator 通用层的，应放到 core 或 tools。
4. 不要为了赶进度新增 tmp_config_runner.py 之类临时入口，并让团队绕过 main.py 使用它。

## 七、agents_library 开发规范

### 7.1 agents 的职责

agents_library 负责生成“实验起点状态”，也就是银行个体、银行间网络、行为层对象、备注信息等初值。它是模拟器的输入，不是模拟器的执行器。

SRS 当前样例中，IB2111 的 agents 生成脚本会写出四类数据：

1. BB：商业银行状态与资产负债表主字段。
2. IB：银行间矩阵、冲击矩阵、违约矩阵。
3. AB：行为层观测、动作、奖励、终止状态。
4. note：备注、策略方法、显示名称、元数据。

### 7.2 set_agents_variables.py 的最低要求

正式的 agents 目录至少应该包含：

1. set_agents_variables.py。
2. 运行脚本后生成的 agents 子目录。
3. logfile.log。

推荐生成脚本结构：

1. 先清理旧的 agents 子目录中的旧文件。
2. 重新生成一批 pkl。
3. 同时生成 logfile.log 作为生成过程记录。

### 7.3 agents 文件名必须与参数表联动

SRS 不是通过目录扫描“猜哪个 pkl 对应哪个实验”，而是根据参数表中的 id_agents、year、density_IB 等字段拼出文件名后直接打开。因此开发者必须保证：

1. parameters.pkl 中参与定位 agents 的列真实存在。
2. 列名与 set_config_variables.py 中的 list_agents_data_filename_para_02 一致。
3. agents 文件命名规则与 Operator 当前拼接逻辑一致。

如果你想把 year 改成 yearName，或者把 density_IB 改成 networkDensity_IB，必须同步更新：

1. parameters 生成脚本。
2. set_config_variables.py 中的 list_agents_data_filename_para_02。
3. 相关文档和样例。

不能只改其中一层。

### 7.4 agents 数据结构规范

对于每类 agent 数据，推荐继续使用“字典序列化为 pkl”的方式，并在字段层面保持稳定命名。原因有三点：

1. 当前 reset_data、初始化逻辑都按字典字段回填。
2. Collector 和模型逻辑默认假设这些字段存在。
3. 输出快照和历史样例已经围绕这一格式积累了大量资产。

新增字段可以，随意删核心字段不可以。尤其是 BB、IB、note 中被模型主过程和可视化依赖的字段，改名前必须做全链路审计。

### 7.5 agents 开发中的禁止事项

1. 不要把 agents 数据写到四件套目录之外的任意临时文件夹，再在 config 中偷偷指过去。
2. 不要在模型运行时动态“补生成”正式 agents 文件，以免实验输入口径漂移。
3. 不要手工修改单个 pkl 作为常规开发手段。应改 set_agents_variables.py 后整体重生。
4. 不要用临时 notebook 生成一批 pkl 后长期不落地为正式 set_agents_variables.py。

## 八、parameters_library 开发规范

### 8.1 parameters 的职责

parameters_library 负责把“一个 agents 初值”扩展成“一批实验任务”。它定义的是实验设计空间，而不是模型执行逻辑。

在现有样例中，parameters 脚本会：

1. 扫描 agents/*.pkl 文件名。
2. 提取 id_agents、year、density_IB 等元信息。
3. 枚举 Shock_exIB_def_t_percentage、Strategy_default、alpha_reward 等参数组合。
4. 生成 DataFrame。
5. 导出 parameters.pkl 和 parameters.xlsx。

### 8.2 parameters.pkl 的最低要求

当前主流程至少要求参数表中存在：

1. exp_id：实验作业编号。
2. id_agents：指向哪一组 agents 初值。
3. 若 agents 文件名依赖 year、density_IB 等列，则这些列也必须存在。
4. 模型运行中会读取的任何业务参数列，例如 Strategy_default、Shock_exIB_def_t_percentage、alpha_reward。

### 8.3 exp_id 的要求

exp_id 是实验作业的主索引。它必须：

1. 在整张表内唯一。
2. 稳定地写入 parameters.pkl。
3. 在后续日志、输出文件名、可视化、筛选条件中保持一致含义。

不要在运行前手工重新排序 parameters.pkl 却不重新生成 exp_id；也不要在参数表里混用多个编号体系。

### 8.4 parameters 开发中的禁止事项

1. 不要在 set_config_variables.py 中临时写一段 DataFrame 构造逻辑替代 parameters.pkl。
2. 不要让 experiments_program.py 直接枚举参数空间，这会破坏职责分层。
3. 不要只生成 xlsx 而不生成 pkl，把慢速回退格式当正式格式。
4. 不要让参数表依赖运行时随机生成却不保存随机种子和结果。

## 九、models_library 开发规范

### 9.1 model 的职责

models_library 是四件套中最容易膨胀的一层。它的职责是实现模型机制本体，包括：

1. 数据结构定义。
2. 财务变量和状态更新方法。
3. 主循环与步进过程。
4. 可选的策略更新逻辑。

它不应该承担以下职责：

1. 选择实验目录。
2. 生成参数表。
3. 生成 agents 文件。
4. 决定全局日志目录或实验输出目录。

### 9.2 当前模型目录的最低接口

一个完整模型目录建议至少包含：

1. __init__.py。
2. model_define.py：定义模型所需的数据结构或类型封装。
3. model_finance.py：定义财务与状态更新函数集合。
4. model_main.py：定义模型主类与主过程。
5. model_strategy.py：若模型含策略层，则提供策略更新类。

### 9.3 当前模型类接口约定

以 Samples/libraries/models_library/model_sample_IB2111 为例，当前默认契约是：

1. model_main.py 中导出 ModelMain。
2. model_finance.py 中导出 ModelFinance。
3. model_strategy.py 中导出 ModelStrategy。

其中 ModelMain 的构造函数签名应兼容：

```python
ModelMain(model_dict, A, A_data, para, sgv)
```

ModelMain 至少应实现：

1. model_process()：整个实验任务的主过程。
2. model_content()：轮次或阶段推进的主体内容。
3. 若模型含动作决策，则实现 model_action()。

这不是抽象意义上的“好建议”，而是当前 experiments_program.py 的真实调用方式。你可以扩展更多方法，但不能把这些最基础的入口方法删掉却不改主调度器。

更严格地说，SRS 中的模型开发应当尽量接近 Gym 环境开发的约束感：框架已经给定正式的类、正式的入口方法和正式的协作位置，开发者主要是在这些既定位置内完成实现，而不是任意发散出一套自己的私有接口面。

因此，IB 系列以及一般 SRS 模型开发都应遵守以下约束：

1. 主流程优先写在 ModelMain 既定方法内，而不是绕出去发明另一套 run_xxx、pipeline_xxx、driver_xxx 主入口。
2. 财务更新优先写在 ModelFinance 既定类内，而不是把核心账务逻辑拆散到 model_main.py 外的大量私有辅助脚本。
3. 策略更新优先写在 ModelStrategy 既定类内，而不是临时再造一套 strategy_engine、decision_runner 之类平行主类。
4. 只有在确实形成可复用、可说明、可长期维护的稳定机制层时，才新增少量辅助方法；新增后也应继续服务于既定主类和既定入口，而不是替代它们。

开发者应把模型代码理解成“在规定题面内作答”，而不是“看到 Python 就自由发挥”。如果主调度器当前认的就是 ModelMain、ModelFinance、ModelStrategy 及其固定方法，那么你的主要实现也应该收敛在这些位置。

### 9.4 model_import_root 与导入策略

Operator 当前默认采用开发优先模式：

1. 始终把模型目录复制一份到实验输出目录做快照。
2. 运行时默认直接从 sgv['folderpath_models'] 导入模型。
3. 只有 runtime_model_import_source='simulator_data' 时，才把模型复制到包内 data/model 并从那里导入。

这意味着当前推荐开发方式是：

1. 在外部模型库或 Samples 的 models_library 中直接开发。
2. 通过 main.py 运行，让 Operator 直接从该目录 import。
3. 用输出目录中的 models 快照做归档和复现，而不是把 data/model 当主要开发目录。

### 9.5 相对导入与包结构

如果模型内部使用相对导入，例如：

```python
from .model_define import ModelAgent
```

那么模型目录必须保持完整包结构，并通过 package import 成功加载。SRS 的 Tools.import_modules_from_package 已对外部工程目录做了一定兼容，但你不能假设任何破碎结构都能被自动修复。

最稳妥做法仍是：

1. 保留 __init__.py。
2. 保持 model_xxx 目录内部是一个正常 Python 包。
3. 避免在模型内部用相对路径读取仓库外随意位置的临时文件。

### 9.6 模型开发中的禁止事项

1. 不要把模型主逻辑放到 tmp_model.py、draft_model.py 之类临时文件里，再靠改正则或改导入器去凑合运行。
2. 不要把 config 解析、agents 生成、parameters 生成写进 model_main.py。
3. 不要为了省事在 model_process() 里偷偷覆盖 para 或 sgv 的全局契约字段。
4. 不要把外部工程的临时路径硬编码进 model 代码，例如 external_paths 的个人绝对路径。
5. 不要在模型目录里无节制地增加一串只服务于当前一次开发的私有主流程函数，例如 run_model_temp()、debug_pipeline()、process_v2()、main_for_test()，最后让真正的正式入口被架空。
6. 不要把本来应写进 ModelMain、ModelFinance、ModelStrategy 既定类方法内的核心逻辑，拆到四处散落的私有函数里，导致阅读者无法沿着既定接口追踪模型。
7. 不要形成“主类只剩空壳，真正逻辑藏在一堆 helper 私有函数”这种结构。对 SRS 来说，这种写法会破坏样例一致性、团队维护性和后续模型迁移。

### 9.7 IB 系列模型的通用建模与开发规范

IB 系列模型指的是围绕银行、银行间敞口、外部冲击、违约传播、资产负债表写回和行为策略展开的一组模型家族，例如 IB1111、IB1211、IB2111、IB2211、IB3111 及其 new、improved 等变体。它们共享一套非常稳定的开发语义，因此不能每做一个新版本就重新发明一套写法。

IB1111 最近一轮改造已经给出一个很明确的结论：IB 系列的新版开发，不只是要在结果上正确，还要在编码风格、状态语义和传播口径上保持系统性一致。这个结论应提升为整个 IB 系列的通用规范。

#### 9.7.1 旧版骨架优先，而不是局部“写爽了”优先

IB 系列新版本默认要尽量沿用对应旧版本的开发骨架。这里的“沿用”不是机械复制，而是保留这些关键一致性：

1. model_main.py 的主流程编排顺序尽量与旧版可对照。
2. 轮次推进、阶段推进、Shock、Loss、Default、State 的调用节奏尽量沿用旧版语义。
3. 对已有字段能复用的，不要轻易引入新的长期局部变量体系。
4. 对银行级中间量，如果它有稳定经济语义，应优先进入 A.BB、A.IB 或 model_define.py，而不是长期滞留在 model_main.py 的局部变量里。

IB 系列模型最忌讳的情况，是为了局部简洁在主流程中堆出大量临时语义变量、辅助函数和绕行分支，最后导致新版虽然“能跑”，但再也无法与旧版逐段对照，也无法让后续维护者理解状态是如何演化的。

因此，IB 系列开发的默认优先级应当是：

1. 旧版骨架优先。
2. 实体字段优先。
3. 局部临时变量最小化。
4. 只有在确实形成新的稳定机制时，才新增明确字段或模块。

#### 9.7.2 `br` 与 `exit` 必须严格区分

IB 系列模型中，`br` 和 `exit` 不是同义词，也不能互相偷换。

1. `br` 表示银行已经被确认破产，但仍然留在系统内，等待后续清算、托管、救助、重组或其他处理。
2. `exit` 表示银行已经完成终局退出，不再参与后续任何经济过程，也不再作为系统主体保留。

当前多数 IB 系列模型尚未显式实现完整清算模块，因此默认语义应是：

1. 破产银行停留在 `br`。
2. `exit` 只在显式清算、显式托管或显式终局退出流程中才被写入。

这条语义必须在整个 IB 系列中保持一致。不能某个模型里 `br` 被当成“已退出”，另一个模型里 `br` 又被当成“待处理破产态”，否则状态表、可视化和后续扩展都会失真。

#### 9.7.3 破产银行默认不再作为新的传播主体

旧版 IB1111 一个最有价值的经验是：一旦银行已经进入破产确认态，就不要再让它反复作为新的传播主体参与循环，否则双边借贷或高耦合网络下很容易出现振荡式衰减、无谓步数增长和语义混乱。

这个经验应推广为 IB 系列的默认规则：

1. 新破产银行可以保留在系统内。
2. 但默认不应继续被纳入新的 `con` 传播源集合。
3. 也不应被纳入新的 `inf` 感染传播核心集合，除非某个扩展模型明确设计了“破产后清算传播”或“破产后残余处置传播”。

换句话说，IB 系列里默认应该阻断的是“破产后继续传播”，而不是“破产后留在系统内”。

#### 9.7.4 对步数增长的判断要区分“传播链变长”和“结算链变长”

IB 系列在引入 stock-flow 写回后，常见现象是 step 变多，但最终 turn 没有增加，或者最终违约结论没有变化。这时不能简单把“步数增加”解释成“传播更强”或“模型更糟”。

必须先判断新增步数来自哪里：

1. 如果来自新的感染、传播、再传播分支，那属于传播链变长。
2. 如果来自 A_P、Z_IB、A_IB、Z_D、A_all、Z_all、E_all 等字段的统一写回与收敛，那属于结算链变长。

对 IB 系列而言，stock-flow 版本常见的是第二种情况：传播结论不变，但会计写回更完整。因此，开发者在比较 old 与 new、baseline 与 improved 版本时，必须同时比较两类结果：

1. 传播结果是否变化，例如 Loss_t、Default_s、Default_IB、Loss_IB_def。
2. 会计终态是否变化，例如 E_all 是否写成真实负值、Z_IB 是否写成剩余债务余额。

不能只凭 step 数量判断模型优劣。

#### 9.7.5 Shock、Loss、Default 与 stock 写回要分层表达

IB 系列模型当前已经明确分成两层：

1. Shock、Loss、Default 这类变量更接近事件流、损失流、违约流视图。
2. A_P、A_IB、Z_IB、Z_D、A_all、Z_all、E_all 这类变量更接近资产负债表主状态，也就是 stock 视图。

这两层必须分开表达，不能混为一谈。

推荐的开发方式是：

1. 先在 Shock、Loss、Default 层明确传播与损失的逻辑。
2. 再通过显式写回步骤，把影响同步到账面 stock。
3. 账面判定和状态判定使用写回后的主状态，而不是永远只看流量变量。

对 IB 系列来说，stock-flow 改造的真正价值，不是“多跑几步”，而是让破产确认、剩余义务、账面权益和后续清算扩展有了真实的落点。

#### 9.7.6 IB 系列中的字段扩展应优先走实体组件

当 IB 系列模型新增中间量或状态时，应优先问两个问题：

1. 这个量是否具有稳定的银行级或边级经济语义。
2. 这个量是否会被多个阶段或多个函数反复使用。

如果答案是“是”，那它应优先进入：

1. A.BB。
2. A.IB。
3. 必要时进入 A.AB 或 note。
4. 并在 model_define.py 中同步声明。

不要因为开发方便，就把本该是实体字段的变量长期塞在 model_main.py 局部作用域里。对 IB 系列而言，这会直接损害可视化、Collector、状态回放和后续模型复用。

#### 9.7.7 IB 系列模型的推荐状态分层

当前建议 IB 系列统一采用三层状态理解：

1. `isv`：资不抵债确认态。
2. `br`：破产确认但仍在系统内等待后续处理。
3. `exit`：完成清算或终局退出，彻底离开系统。

只要模型还没有显式的清算模块，就不要把 `br` 自动折叠成 `exit`。这样做虽然在某些样本上看起来更容易“收敛”，但会直接抹掉后续最重要的扩展空间：

1. 破产后清算。
2. 破产后救助或重组。
3. 破产后托管与分阶段退出。

#### 9.7.8 IB 系列的结果校验不能只看一个口径

对 IB 系列模型做 old/new 或版本迁移比较时，至少要做三层校验：

1. 传播结论层：最终违约集合、最终损失量、最终违约量是否一致或符合预期差异。
2. 会计终态层：E_all、Z_IB、A_IB、Z_D 等账面字段是否按新口径真实写回。
3. 状态机层：`inf`、`con`、`isv`、`br`、`exit` 是否符合统一语义，没有出现语义塌陷。

只有同时看这三层，才能判断一个 IB 系列改造是“真的更完整”，还是只是“表面上还在出数”。

#### 9.7.9 IB 系列开发中的额外禁止事项

除了一般 models_library 禁止事项外，IB 系列还应额外避免：

1. 为了减少步数，直接把 `br` 映射成 `exit`。
2. 为了减少代码量，把旧版字段体系整体替换成一套局部临时变量体系。
3. 为了省事，把 stock 写回逻辑散落在多个临时脚本或 notebook 里，而不是回到正式 model_main.py 和 model_finance.py。
4. 只比较 step 数，不比较最终传播结果和最终账面状态。
5. 只让新版“数值接近”，却放弃与旧版主流程骨架的可对照性。

## 十、四件套之外，哪些代码应该放进 Simulator 内核

很多开发者在模型开发过程中，会纠结一段逻辑到底该放在 model_xxx，还是放在 SystemicRiskSimulator/core。判断标准很简单。

如果一段逻辑满足下面任一条件，它更适合进入 Simulator 内核：

1. 它不依赖某个具体模型家族，而是多个模型都通用。
2. 它的职责是调度、导入、复制、导出、日志、序列化、路径解析、阶段组织。
3. 它是对现有多模型都可复用的算法封装。

如果一段逻辑满足下面任一条件，它更适合留在 models_library：

1. 它的变量命名、状态更新、经济含义只服务于某个模型家族。
2. 它只对某个机制成立，例如特定的银行间违约传播策略。
3. 它依赖某个模型自己定义的字段和行为语义。

简化地说：

1. 通用编排进 core/tools/programs。
2. 具体经济机制进 models_library。
3. 具体实验设计进 parameters_library。
4. 具体初始样本进 agents_library。
5. 具体运行开关进 configs_library。

## 十一、开发一个新模型家族的标准流程

### 11.1 第一步：先决定四件套目录名

例如你要开发 IB3111_new，则先创建：

1. config_xxx。
2. agents_xxx。
3. parameters_xxx。
4. model_xxx。

不要一上来先写 tmp_run_new_model.py。先把正式资源骨架立起来。

### 11.2 第二步：先完成 models_library 骨架

至少先建立：

1. __init__.py。
2. model_define.py。
3. model_finance.py。
4. model_main.py。
5. 若需要，model_strategy.py。

并让 ModelMain 的构造与 model_process() 可以被 experiments_program.py 成功调用。

### 11.3 第三步：建立 agents 生成脚本

确认你的模型初值需要哪些对象。当前银行类样例一般是：

1. BB。
2. IB。
3. AB。
4. note。

如果你需要新对象，也可以加，但必须同步让模型和 Collector 知道如何处理。不要只在 agents 里生成一个新对象却没人读取。

### 11.4 第四步：建立 parameters 生成脚本

最少先做一份小规模参数表，只覆盖 1 到 3 个样本点，确保主流程能跑通，然后再扩参数空间。不要第一天就生成十万条组合，把排错难度抬满。

### 11.5 第五步：建立 config 并走 main.py 跑通

只要你的主流程不是从 main.py 跑通的，就说明你还没有真正接入 SRS。开发阶段可以单独调 ModelMain，但正式接入完成的标准，必须是 main.py 可以完整拉起这套四件套。

### 11.6 第六步：验证实验快照与输出目录

检查 outputlog 下是否已经包含：

1. config 快照。
2. agents 快照。
3. parameters 快照。
4. models 快照。

如果只有结果，没有快照，那不是合格的 SRS 接入。

## 十二、关于外部工程接入

SRS 支持从外部工程读取四件套资源。当前最稳妥的方式是外部工程也提供一个 libraries 目录，并继续使用四件套布局。

当前外部工程接入的关键点有：

1. folderpath_config 可以是外部绝对路径。
2. 当路径命中父目录名为 libraries 时，SRS 会尝试把外部工程根路径锚定到 libraries 的父目录。
3. 外部 set_config_variables.py 中的 folderpath_models、folderpath_parameters、folderpath_agents 最好写成相对外部工程根目录的路径。

你要记住一个原则：对 SRS 来说，外部工程不是“例外模式”，而是另一套四件套来源。只要目录契约稳定，它就应该像 Samples 一样被运行。

## 十三、严禁用临时程序代替四件套主程序

这是本指南最重要的约束之一。

可以存在临时脚本，但临时脚本只能做以下事情：

1. 快速试验某段算法。
2. 排查某个 pkl 或某个 DataFrame 的局部问题。
3. 做一次性数据修复，再把逻辑回写到正式脚本。

临时脚本不能成为：

1. 正式参数生成器的替代品。
2. 正式 agents 生成器的替代品。
3. 正式模型入口的替代品。
4. 正式 README 和用户手册中宣传的使用方式。

出现以下情况时，说明你已经偏离规范：

1. 团队成员运行实验时，不再执行 set_agents_variables.py 或 set_parameters_variables.py，而是执行某个 tmp_prepare.py。
2. 运行实验时，不再通过 main.py，而是执行某个 run_debug_only.py。
3. 你自己已经说不清“正式的 config 在哪里、正式的参数表在哪里、正式的模型入口在哪里”。

SRS 的开发允许调试便利，但不允许把调试便利变成正式架构。

## 十四、调试规范

### 14.1 调试优先入口

调试时优先使用：

1. is_develope_mode=True。
2. 通过 main.py 运行。
3. 在 IDE 中对 ModelMain、Operator、Collector、Executer 打断点。

这样做的好处是：

1. 你仍在走正式入口。
2. 你仍在使用正式四件套。
3. 你调试到的是将来真正会被运行的那条链路。

### 14.2 常见排查顺序

如果实验跑不起来，推荐按这个顺序排查：

1. 先看 main.py 打印出的最终 config 是否正确。
2. 再看 folderpath_config、folderpath_models、folderpath_parameters、folderpath_agents 是否指向真实目录。
3. 再看 set_config_variables.py 的运行开关是否符合预期。
4. 再看 parameters.pkl 是否存在、列名是否齐全。
5. 再看 agents 子目录中的 pkl 文件名是否与参数表匹配。
6. 最后才进入 model_main.py 看模型逻辑。

很多所谓“模型错误”，其实只是前置四件套没有对齐。

## 十五、提交前检查清单

在你提交任何与 SRS 开发相关的改动前，请至少逐项检查以下事项：

1. 是否仍然通过 main.py 作为正式入口运行。
2. 是否仍然保留四件套分层，没有被临时脚本取代。
3. 新增配置是否写在 set_config_variables.py，而不是散落到多个隐蔽文件中。
4. 新增 agents 是否能通过正式 set_agents_variables.py 重生。
5. 新增参数是否能通过正式 set_parameters_variables.py 重生。
6. 新增模型是否仍兼容 model_main、model_finance、可选 model_strategy 的导入方式。
7. 输出目录是否正确生成快照。
8. 是否去除了不该提交的本机绝对路径。
9. 是否更新了对应文档，而不是只改代码。

## 十六、开发者的最低共识

最后用一句话概括 SRS 的开发准则：

开发者可以灵活试验，但正式运行必须回到统一入口、统一四件套、统一快照、统一契约。

如果某个改动让实验更快，却让目录更乱、职责更混、入口更多、快照更弱，那它就不是对 SRS 的改进。

如果某个改动让开发者更容易新建模型、理解四件套、复现实验、定位错误，即使它多写了一些规范和样板，它仍然是值得做的。
